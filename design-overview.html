IPL Franchise Store blueprint

An e-commerce store for official IPL merchandise: jerseys, caps, flags, autographed photos and accessories from all ten franchises. .NET 8 Web API on Clean Architecture, EF Core over PostgreSQL 16, and a plain React client. It is designed so a race, a retry or a live requirement change never breaks correctness.

Architecture

Clean Architecture, dependencies point inward

Domain has zero dependencies. Application owns the use cases and the interfaces (ports). Infrastructure implements them with EF Core and PostgreSQL. The API is a thin HTTP adapter and the single composition root where DI and options binding live.

Request flow

Checkout in one retried transaction

Lock the customer's cart, check the idempotency key, reserve stock with one conditional UPDATE per line in id order, snapshot the lines, price with the same strategy the cart preview uses, then commit. Any failure rolls back every reservation.

sequenceDiagram
    autonumber
    participant UI as React CartPage
    participant C as OrdersController
    participant S as CheckoutService
    participant U as EfUnitOfWork
    participant DB as PostgreSQL
    UI->>C: POST /api/v1/orders<br/>X-Customer-Id, Idempotency-Key: K
    C->>S: PlaceOrderAsync(PlaceOrderCommand)
    S->>U: ExecuteInTransactionAsync(work)
    loop retried as a whole on transient errors (ResilienceOptions)
        U->>DB: BEGIN (READ COMMITTED)
        S->>DB: INSERT carts ... ON CONFLICT DO NOTHING
        S->>DB: SELECT ... FROM carts WHERE customer_id=@c FOR UPDATE
        S->>DB: SELECT order WHERE (customer, K)  -- replay?
        S->>DB: UPDATE products SET stock=stock-q WHERE id=@p AND stock>=q (per line, ordered by id)
        S->>DB: INSERT orders, order_items · DELETE cart_items
        Note over DB: triggers refresh product_catalog (same tx)
        U->>DB: COMMIT
    end
    S-->>C: CheckoutResult(order, isReplay)
    C-->>UI: 201 Created (or 200 + Idempotent-Replayed: true)

Database

ER model: normalised writes, denormalised reads

The write model is in 3NF. product_catalog is a flat, trigger-maintained projection updated in the same transaction. order_items snapshot what was bought, and customer_id is copied onto child rows as the future shard key.

Resilience

What is retried, and why it's safe

The browser retries only idempotent calls or keyed POSTs. The API re-runs the whole transaction on transient PostgreSQL errors, with backoff from ResilienceOptions. If a commit is ambiguous, the idempotency key turns the re-run into a replay.

flowchart LR
    subgraph Browser
        A[httpClient] -->|GET/PUT/DELETE or POST with Idempotency-Key<br/>on network error / 408 / 429 / 5xx<br/>exp. backoff + full jitter, max 3| A
    end
    subgraph API
        U[EfUnitOfWork] -->|whole transaction on transient DB errors<br/>40001, 40P01, 57P0x, 53xxx, socket/timeout<br/>exp. backoff, MaxRetryCount=3| U
        M[Migrator] -->|DB not reachable at start-up<br/>StartupConnectAttempts=15| M
    end
    A --> U
Scale

Distributed database path

Zone-redundant HA gives RPO 0. An async read replica serves catalogue browsing through ReadOnlyStoreDbContext, while carts and orders read the primary for read-your-writes. Next steps are Citus sharding by customer_id and monthly partitions for orders.
